## ТЕСТИРОВАНИЕ СЕРВИСА АРЕНДЫ САМОКАТОВ

# Коллега, для установки зависимостей выполни команду: 

    pip3 install -r requirements.txt


# Для запуска теста с созданием отчётов Allure запусти поочерёдно:
    
    *Для тестирования:
    pytest --alluredir=allure_results
    
    *Для визуализации отчётов:
    allure serve allure_results
    
    *Для визуализации отчётов в конкретной папке:
    allure generate C:\***адрес***\allure_results -o C:\***адрес***\Allure_Report
    
    *Чтобы открыть отчёт запустите в терминале:
    allure open Allure_Report


## Найденные дефекты

**Поле firstName не обязательно при создании курьера**
    
Документация помечает `firstName` как обязательное,
    фактически `POST /api/v1/courier` без него возвращает 201 `{"ok": true}`.
    
Тест `test_create_courier_without_required_field_returns_400` помечен `xfail` до исправления.


**Запрос на логин без поля password висит минуту и возвращает 504 вместо 400**
Речь идёт о `POST /api/v1/courier/login`
    Но если передать пароль пустой строкой, ручка отвечает корректно.
    Баг именно на отсутствующем поле, а не на пустом значении.

Тест `test_login_courier_without_required_field_returns_400` помечен `xfail` до исправления.


**Заказ с одним цветом падает с 500, если отправлять его формой**
Речь идёт о `POST /api/v1/orders`
    Если передать `color` как обычную форму (`data=`), список из одного
    элемента превращается в строку — сервер получает `color=BLACK`
    вместо `["BLACK"]` и падает с
    `{"code":500,"message":"values.map is not a function"}`.
    Пустой список при этом вообще пропадает из запроса.

В тестах цвет передаётся через `json=` — так все четыре вариант (BLACK, GREY, оба, ни одного) работают корректно.
*Отдельным тестом баг не покрыт: нашёл при ручной проверке в Postman.


**Удаление курьера без id возвращает 404 вместо 400**
Речь идёт о `DELETE /api/v1/courier/:id`
    В документации сказано, что должна прийти ошибка 400
    «Недостаточно данных для удаления курьера», а по факту приходит
    `{"code":404,"message":"Not Found."}` — и со слешем на конце, и без него.
    Похоже, id это часть адреса, поэтому без него сервер просто
    не находит нужный маршрут и до проверки данных дело не доходит.

Тест `test_delete_courier_no_id_returns_400` помечен `xfail` до исправления.


**Принятие заказа без id заказа возвращает 404 вместо 400**
Речь идёт о `PUT /api/v1/orders/accept`
    В документации сказано, что должна прийти ошибка 400 «Недостаточно данных для поиска»,
    а по факту приходит `{"code":404,"message":"Not Found."}`.

Тест `test_accept_order_no_order_id_return_400` помечен `xfail` до исправления.


**Номер заказа больше 2147483647 роняет сервер с 500**
Речь идёт о `GET /api/v1/orders/track`
    Если передать `t=9876543210`, приходит
    `{"code":500,"message":"value \"9876543210\" is out of range for type integer"}`.
    До 2147483647 включительно всё нормально — приходит 404 «Заказ не найден».
    Похоже, номер заказа в базе это 32-битное целое, и сервер не проверяетвходное число перед запросом в базу.
    Заодно наружу попадает текст ошибки базы данных — это уже уязвимость.

Отдельным тестом баг не покрыт: нашёл случайно, когда подбирал несуществующий номер заказа.
